# 0.7 plan — dashboards that reach people, agents you can trust

0.6 made the warehouse answerable over MCP, from a catalog built out of the
SQL people already wrote. 0.7 closes the gaps that decide whether a team
adopts it: dashboards that arrive without anyone opening SQLDesk, a way in
for SSO shops that is not a personal API key, answers grounded in what
people have agreed, a path for that agreed meaning into Cube, a first page
that loads fast, and control over who gets which feature.

Scope decided with Iqbal on 2026-09-27. No date is set; 0.6.0 ships first.

## Settled

- **In:** scheduled subscriptions, OAuth 2.1 for MCP, semantic layer part 2,
  sharing a dashboard to Slack (§8), Kafka streams and the storage lifecycle
  (§9), frontend load time, feature permissions, and every small item
  listed at the end (cleanups, chart and ops, small features, housekeeping).
- **Cube is where proven meaning ends up.** Questions get answered in
  SQLDesk first; what works and people agree on moves to Cube; a model asks
  Cube first and SQLDesk only for what Cube does not have yet. The YAML we
  export must load in a real Cube, and whatever Cube needs that SQLDesk
  cannot know for certain (keys, join direction, credentials) is asked of a
  person, never guessed.
- **Slack: SQLDesk posts it, and the button opens the public link** (§8).
  No link previews (B) or Socket Mode unfurls (C).
- **A stream is a window, never a pipeline** (§9). SQLDesk keeps minutes of
  raw events and rolls the rest up; for history, land the topic in a
  warehouse and point SQLDesk at that.
- **Uploads expire after 7 days** unless somebody with the permission keeps
  them, and the install has a byte quota (§9). "Organization" is Redash's
  tenancy row, not a thing SQLDesk users have: `SQLDESK_MULTI_ORG` is off,
  there is exactly one, and nothing a person reads should name it.
- **Cube both ways.** The chart can run a Cube as an optional add-on, and
  SQLDesk can connect to a Cube you already run by URL and secret (§7).
- **Out, to 0.8 or later:** row-level security, push instead of poll (SSE),
  notebooks, an in-app chat assistant, OSI/Ossie export, MCP write tools,
  and **Cube** -- designed in §7, deferred so Kafka fits. Nothing here is
  designed to make those harder.
- **Multi-organization cleanup is 0.8** (decided 2026-09-29). SQLDesk
  carries Redash's tenancy model, ships with `MULTI_ORG` off, and runs its
  tests with it *on* -- so the route shape CI exercises is not the one
  anybody deploys. The cleanup keeps the `org_id` scoping, which is real
  defence and is tested; says plainly in the docs that running more than one
  organization is unsupported; runs CI in the shipped configuration as well;
  and fixes the admin endpoints that reach across organizations, which are
  wrong either way. It does **not** remove the model: that is a sixteen-table
  migration which buys simplicity nobody needs and closes the hosted door.
- **Kafka is in, Cube is out.** Cube is an integration path with nobody
  waiting on it, and §3 delivers most of its value without a new service.
  Streams are the thing being asked for.
- **Feature permissions are per group, never per user.** One permission
  model: a user has what their groups grant. One person who needs a feature
  goes into a group for it.
- **After upgrading, only admins have MCP.** Everyone else is granted it
  through a group. rc.2 users other than admins lose MCP until then, and
  the CHANGELOG says so.
- **One catalog permission**, "Curate the catalog". No separate read-only
  view: the catalog reaches people through MCP answers already.

Still open, each with a recommendation below:

- [ ] Subscriptions to Slack in 0.7, or email only (§1). §8 brings the
      Slack app into 0.7 anyway, which makes this one small.
- [ ] Token lifetimes for OAuth (§2).
- [ ] Whether production source maps keep shipping in the image (§6).

### Where it stands (2026-10-01)

Done, on `release/0.7`, each with a regression test that fails without it and
mutation testing on the assertions that matter:

- **§5 permissions, §4 load time, §6 cleanups.** Initial load 931 → 522 KB
  gzipped, budget ratcheted to 560 KB. Server resident memory 273 → 175 MB by
  importing a query runner's SDK when it is used rather than at startup.
  Renderer image 953 → 517 MB compressed.
- **§1 subscriptions.** Verified end to end with a real send: PNG inline, a
  one-page A4 PDF attached, one-click unsubscribe. Blank captures went from
  three in ten to none -- `full_page=True` resizes the viewport and shoots
  immediately, which was the fault behind three wrong hypotheses about CSS
  chunks and page readiness.
- **§2 OAuth 2.1 for MCP.** Discovery, authorization code with PKCE (S256
  only, enforced ourselves because authlib's `required=True` does not),
  refresh with rotation, revocation, dynamic client registration, a consent
  page behind the ordinary login, Connected apps on the profile and under
  Admin → MCP. Tokens stored hashed. **Not done: Client ID Metadata
  Documents.** A CIMD fetch is an outbound request to a URL the client
  supplies, so doing it safely needs a resolver that refuses private address
  ranges and redirects, and a real client to test against. DCR is what every
  current client uses and is what landed.
- **§3 semantic layer part 2.** Agreed measures before the schema,
  `find_measures`, confirmed queries ranked first and labelled, a staleness
  policy the tools warn with and the Catalog page shows, `manage ai eval`
  with a questions file and a nightly score.
- **§9A uploads get a life.** Unload at three days, warn at six, delete at
  seven and only what was warned about; `keep_uploads`; a byte quota that
  says the figures; Admin → Storage.

  Two faults in it found on a real install (2026-10-02) and fixed. Unloading
  hid a file from `get_schema`, so a file sitting on the disk was invisible to
  both the catalog harvest and the editor's schema browser -- the harvest found
  an empty schema, kept the old entries rather than emptying them, and the
  Catalog page went on saying "last harvested 7 days ago" however often
  somebody pressed Harvest. Reading the schema is the one operation where the
  inference unloading avoids is the whole point, so every file is brought back
  for the read and unloaded again after it. And an upload whose file is not on
  the disk at all -- the record outliving the volume it was written to -- now
  says so on Storage and on the data source, instead of leaving somebody with
  a schema that is silently empty.

- **§8 Share to Slack.** Settings → Slack takes the app's bot token, checked
  against Slack before it is stored and encrypted with the data source key.
  Share → Send to Slack picks a channel from the list Slack gives, uploads a
  picture of the dashboard and posts it with an Open dashboard button. Nothing
  reaches in, so it works behind a VPN. **Not verified against a real
  workspace** — driven against a stub of Slack's Web API, which covers the
  three-step upload, the pagination and the error translation, but not whether
  a real Slack renders the blocks as intended. That needs a bot token.

- **§9B streams, the server half.** A topic is a data source; the window is
  whatever the row budget buys at the rate observed; events over the ceiling are
  sampled on a hash of the key's bytes and every chart says so; per-minute
  rollups with the group count capped and the tail shown rather than hidden; a
  consumer per active stream, started by a supervisor under a Redis lock, which
  seeks to the end on every start. `confluent-kafka` is in the optional
  dependency group with every other SDK, so an install with no streams carries
  none of it and `kafka_stream` simply does not register.

  **Not run against a real broker.** Kafka is behind one class, `Broker`, and
  everything above it is driven in tests by a fake that returns bytes — the
  sampling, the flush, the window, the rate, the schema, the rollup, the lock.
  What that cannot tell us is whether librdkafka behaves as `Broker` assumes:
  the seek-to-end on a group with a committed offset is the part most worth
  watching. Needs a broker to run against; redpanda in compose is the cheap
  way.

  **Admin → Streams** shows what each topic is doing and, above all, *why* a
  quiet one is quiet: paused, broken, and genuinely empty are three different
  situations that look identical on a chart. The pin, the row budget and the
  events-per-second ceiling are set there. Verified against a real broker
  (`make stream-tests`, redpanda behind a compose profile) -- including the
  assumption a fake can only agree with: a consumer group that has already run
  still starts at the end of the topic.

- **§6 small features, all four.** A queue per data source on its own page
  instead of the `UPDATE data_sources` the Administration page used to
  prescribe. A cost ceiling on MCP `run_query`, from the engine's own estimate
  — a plan cost from the Postgres family, dry-run bytes from BigQuery — where
  no estimate is never a refusal. **My MCP** in the profile menu, carrying only
  one's own calls and never the question or the SQL; System Status out of it,
  since it is in the Admin menu now. And **query version history**: a History
  dialog with the versions, a diff either way round, and a restore that writes
  a new version rather than rewriting one.

  The history needed a repair underneath it first. `changes` has recorded
  queries being created and archived since long before this fork and never
  recorded one being **edited** — the handler set a `changed_by` that nothing
  read — so the table looked well kept and held almost nothing. Two further
  faults only showed up once something read it: the `previous` half of a record
  was wrong for every field but the last one set, and `Change.last_change`
  returned the oldest record rather than the newest, because a query's
  `version` column does not move when it is edited.

With that, **§6 is complete** — the cleanups and the chart-and-ops items were
already in place and the plan's own section had simply not been marked.

## §1 Scheduled subscriptions

Email a dashboard on a schedule, as a picture or a one-page PDF. The gap
Metabase and Superset both close in their open-source editions, and the one
market research ranked closest to a blocker.

**What people do:** Share → Subscribe. Choose when (the query schedule's
existing shapes: every N hours, daily at a time, weekly on a day), who
(people in the organization), and PNG or PDF. A subscription list on the
dashboard shows who gets it; each recipient can unsubscribe from the email.

**Built from what exists:**

- *Rendering.* The screenshots service (0.5) draws the page; it gains a
  `format: pdf` that prints one A4-landscape page with Chromium's own PDF
  output, so a PDF is text, not a photograph of text.
- *One page.* The rule export uses — at most 12 widgets, one page shrunk by
  at most 30% — is checked when the subscription is saved and again before
  each send. A dashboard that grows past it stops sending and tells its
  owner, rather than sending something unreadable.
- *Email.* `destinations/email.py` already attaches images inline for
  alerts. Subscriptions reuse that path.
- *Scheduling.* A periodic job every minute, beside `refresh_queries`,
  enqueues due subscriptions on the `emails` queue.

**What is new:**

- A `subscriptions` table: dashboard, owner, schedule, format, recipients
  (user ids, not addresses), `last_sent_at`, `last_error`, active.
- **The renderer stops needing a public link.** Today it opens a dashboard
  through `/public/dashboards/<token>`, so an alert can only picture a
  dashboard that has been shared publicly. A subscription must not make a
  dashboard public. Instead the worker mints a signed, single-use pass that
  is good for one dashboard, for five minutes, as the subscription's owner,
  and only for reads. Alerts move to the same pass, and "a dashboard is drawn
  only if it has been shared" comes out of the docs.
- *Data freshness:* a subscription sends the latest stored results and says
  how old they are in the email. Refreshing every query first would turn a
  subscription into a warehouse bill nobody asked for; an owner who wants
  fresh numbers gives the queries a schedule.

**Who may do it.** A new feature permission, "Send dashboards" (§5), which
also covers sending to Slack (§8).
Recipients are people in the organization, chosen from the user list, never
free-typed addresses: a subscription is otherwise a way to mail a
dashboard's contents anywhere. Each recipient must be able to see the
dashboard; the owner is told who was left out and why.

**Requires the Rendering add-on.** Without it the Subscribe item is not
shown, and the Deploying page says so.

**Open: Slack.** Slack's incoming webhooks cannot carry a file, which is why
alerts to Slack have no picture. Sending one needs a Slack app with a bot
token and file uploads. §8 adds exactly that app to 0.7 for sharing, so a
subscription to a Slack channel becomes a small addition on top of it.
Recommendation: include it once §8 works.

**Verify:** a subscription sends on schedule with the picture inline and
the PDF attached (Mailpit, as for alert screenshots); a too-big dashboard is
refused at save and stops at send; a recipient without access is left out
and the owner told; the pass cannot open a second dashboard, cannot write,
and expires; the renderer no longer needs a public link for alerts.

**Done, through a real send** (2026-09-30). Against the development cluster,
with the renderer and a Mailpit of its own: a PNG subscription arrived with a
2800x1800 picture of the dashboard inline under `cid:sqldesk-dashboard`, the
body saying how old the numbers were and who subscribed the reader; the same
subscription as a PDF arrived with a one-page A4 landscape attachment and no
inline image. `last_sent_at` set, `last_error` null, both times.

Left to build: the Share → Subscribe interface, and per-recipient
unsubscribe links.

### Closed: a capture that missed its charts

Rendering a dashboard of eighty widgets produced one of two byte-identical
images, about three times in four the right one and once in four a grid of
five charts and seventy-five empty rectangles.

**It was never the page.** Three attempts at making the page's readiness
stricter -- a correct `ready` signal, a floor on the settle window, a check
that off-screen charts had been revealed, and finally each chart reporting
ECharts' own `finished` event -- moved it from a half to a quarter and then
stopped. Instrumenting the page settled it: *every* run, including the ones
that came back blank, reported 47 charts mounted, 0 pending, 54 canvases,
settled in 1.5 seconds. The page was drawn when it said so.

It was the capture. `screenshot(full_page=True)` stretches the window to the
whole document -- 21,574 pixels here -- and shoots immediately. That resize
re-lays-out every chart, ECharts redraws asynchronously, and the picture was
taken mid-repaint.

So the renderer stretches the window *first* and then asks the page again,
and the page withdraws its "drawn" attribute on a resize and settles afresh.
Ten captures in a row, all correct, where before three of ten were not.

The lesson worth keeping: four rounds of making a signal stricter, when one
measurement of what the signal actually said would have pointed somewhere
else entirely.

## §2 OAuth 2.1 for MCP

MCP today authenticates with a personal API key pasted into a client. For a
team that signs in with JumpCloud, that is a long-lived secret outside SSO:
not revoked when someone leaves, not visible in the identity provider. With
OAuth the client opens a browser, the person signs in through SQLDesk's
usual login — which is SSO where SSO is configured — and the client gets a
short-lived token tied to that person.

**Built to the MCP authorization spec (2025-06-18, updated 2026-07-28):**

- SQLDesk is both the resource server and the authorization server.
- Discovery: `/.well-known/oauth-protected-resource` (RFC 9728) and
  `/.well-known/oauth-authorization-server` (RFC 8414). `/mcp` answers 401
  with `WWW-Authenticate` pointing at them, which is how clients find out
  to start the flow.
- Authorization code with PKCE (S256 only), refresh tokens, no implicit
  flow, no client secrets for public clients.
- Client registration by Client ID Metadata Documents, as the 2026-07-28
  spec prefers; Dynamic Client Registration only if the clients we test
  still need it.
- `authlib` is already a dependency and carries an authorization server for
  Flask, so this adds no library.

**Consent and control:** the consent page names the client and what it will
be able to do (read-only, as this user). A "Connected apps" section on each
person's profile lists clients with tokens, when each was last used, and a
Revoke button; admins see and revoke everyone's under Admin → MCP. Disabling
a user revokes their tokens. Every audit row records the client.

**API keys stay.** Scripts and headless setups need them, and behind a VPN
they are fine. OAuth is the recommended way for people.

**What OAuth does not fix:** hosted connectors in chat apps are fetched from
the vendor's servers, so the endpoint still has to be reachable from the
internet. The MCP guide says this plainly, as the blog already does.

**Open: token lifetimes.** Recommendation: access token 1 hour, refresh
token 30 days sliding, both revoked with the user.

**Verify:** Claude Code and one other client complete the flow against the
minikube install; a token stops working when revoked or the user is
disabled; PKCE is required; a token from one organization is refused in
another; the flow goes through SAML login when SAML is on.

## §3 Semantic layer, part 2

0.6 finds tables by usage and proposes measures from saved SQL. Part 2 makes
agreed meaning come first, so a model starts from what people have signed
off on and reaches for raw SQL only when nothing agreed fits. The research
behind it: semantic layers' failures are loud errors where text-to-SQL's are
plausible wrong answers.

- **Agreed measures first.** `find_context` opens with the agreed measures
  on the tables it found — name, what it computes, which table — before the
  table cards. A new tool, `find_measures(question)`, looks them up directly.
- **Verified queries.** A curator marks a saved query as the right answer to
  its question. `find_queries` ranks verified queries first and says they
  are verified; the Catalog page lists them; export writes them beside the
  cube files.
- **A retrieval check that runs without a model.** A YAML file of questions,
  each with the tables, measures or queries a good answer must include.
  `manage ai eval` runs them through the same retrieval MCP uses and reports
  what was missed; the scheduler can run it nightly after the harvest and
  put the score on the Catalog page. Deterministic, so it is a test, not a
  benchmark — and it is how "the catalog got worse" gets noticed.
- **Staleness.** `harvested_at` exists; the policy does not. A data source's
  catalog older than three harvest intervals is marked stale on the Catalog
  page, and `find_context` says so in its answer.

**Verify:** tests per tool that agreed and verified entries rank first; the
eval command fails when an expected table is missing; the Catalog page shows
the score.

## §4 Frontend load time

931 KB gzipped loads before a dashboard draws, which is 8.1 MB of parsed
source. Measured from a production build's own stats on 2026-09-29 rather
than estimated, because two of the guesses above it were wrong:

| In the initial load | Parsed | Share |
|---|---|---|
| SQLDesk's own code | 1,686 KB | 20% |
| **ace-builds** (the SQL editor) | **1,076 KB** | **13%** |
| CSS | 1,038 KB | 13% |
| lodash | 639 KB | 8% |
| antd | 595 KB | 7% |
| moment | 193 KB | 2% |

**ECharts is already out of it.** Every visualization declares `load()` and
arrives in its own chunk, so the 5.1 MB of ECharts and 677 KB of zrender --
a quarter of everything the build touches -- are fetched when a chart is
drawn and not before. That work is done; the plan should stop listing it.

**Ace is the prize.** A megabyte of SQL editor reaches everyone who opens a
dashboard, a list or the settings, because `client/app/pages/index.js`
imports all thirty-odd pages at startup so each can register its route.
Every page's dependencies are therefore everyone's dependencies.

- **Route-level code splitting, which is the whole of it.** A page's route
  registration has to stop importing the page: the path and title move to a
  table, and `render` returns a `React.lazy` component. `routes.ts` already
  types `render` as returning a node, so nothing there has to change --
  but `Router.jsx` has no `Suspense` boundary yet, and needs one.
- Then the query editor, the schema browser and the export code follow
  their pages out of the initial load.
- One copy each of axios, the rc-* packages and react-draggable; lodash
  imported per function.
- Stop shipping source maps in the image (§6, open).

**Staged, because it touches every route:** the boundary and one page
first -- the query editor, which is the megabyte -- measured and verified
before the rest follow.

**Target:** set from a measured baseline before starting, with the numbers
and the method written into `docs/performance.html`, as for every 0.x
performance change. A budget check in CI fails a build that grows the
initial load past it.

**Verify:** the performance page records before and after; the Cypress
suite passes unchanged; a dashboard page's first load is measured in
headless Chrome, not in the hidden browser pane, whose timers are throttled.

## §5 Feature permissions

Admins decide who gets which feature, per group, on the Group page — the
place "Members can make dashboards live" already lives. That checkbox
becomes the first entry in a list.

**One list on the server** (`sqldesk/features.py`): each entry has a name,
a label, a one-line description, and the setting that switches the feature
on at all. The group permissions endpoint accepts anything in the list; the
Group page draws one checkbox per entry the install has switched on. Adding
notebooks later is one entry and one check.

| Permission | Label | Gates |
|---|---|---|
| `manage_live_dashboards` | Make dashboards live | exists since 0.4 |
| `use_mcp` | Connect AI clients over MCP | `/mcp`, the MCP page and menu item, OAuth consent |
| `manage_catalog` | Curate the catalog | Catalog page and its endpoints: descriptions, measures, verified queries, export |
| `send_dashboards` | Send dashboards (email and Slack) | Share → Subscribe (§1), Share → Send to Slack (§8) |
| `keep_uploads` | Keep uploaded files past 7 days | The Keep button on an upload (§9) |

Admins have every permission. **No group gets the new ones by default**, so
after the upgrade only admins have MCP.

- **Enforcement** goes through one function, `can(user, feature)`, used by
  handlers and by the client's `currentUser.can(...)` alike.
- A refused MCP call writes an audit row, "no MCP permission", like a bad
  key does.
- The Catalog page moves out of the super-admin-only area so a curator who
  is not an admin can reach it. Harvesting stays admin-only (the Catalog
  page's Harvest button, from 0.6.0-rc.3): it reads every source's schema
  on the worker, which is an admin's call.
- **The user page gains an Access section,** read-only: each feature, and
  which group grants it, plus a summary of data source access. Changing it
  means changing groups, and the section says so.
- **Kafka is not a checkbox.** A topic is a data source, and data sources
  are already granted per group, view-only included (§9).

**Verify:** per-feature handler tests for admin, granted, and not granted;
the Group page's checkboxes come from the server list; revoking `use_mcp`
refuses the next MCP call; the migration leaves existing group permissions
alone and grants nothing new.

## §7 Cube: proven meaning moves there (designed, deferred to 0.8)

*Kept here because the design is settled and the work is real; it moves out
of 0.7 only so Kafka fits. Nothing below changed.*

The loop, from least trusted to most:

1. **Explored in SQLDesk.** Raw SQL, tables found by usage, proposed
   measures. Where a new question gets its first answer.
2. **Proven in SQLDesk.** A query that runs and that a curator has marked
   verified, and a measure somebody has agreed (both §3).
3. **In Cube.** What was proven, exported as Cube's data model and loaded
   into a Cube.

A model asks Cube first. When Cube has nothing that fits, it falls back to
SQLDesk's catalog, and every answer says which layer it came from. A
SQLDesk answer people keep using is what gets proven and moved up next.

### A. An export a real Cube loads

Today's export is Cube-shaped and has never been loaded into Cube. What is
known to be wrong or missing:

- **No primary keys.** Cube refuses a join unless both cubes have a
  `primary_key` dimension. The harvest does not read keys at all.
- **Join direction is a guess.** Every relationship is written from both
  ends as `many_to_one`, so one end is always wrong.
- **No `data_source`.** With more than one SQLDesk data source, Cube cannot
  tell which database a cube lives in.
- **Unquoted column SQL.** `sql: name` breaks on mixed-case, spaced or
  reserved column names; write `{CUBE}."name"` in the engine's quoting.
- **Name collisions** after slugging (`public.orders` and `public_orders`)
  are silently the same cube.

The harvest reads declared primary keys where the engine has them
(Postgres, MySQL, SQL Server, and others through `information_schema`),
which settles the key for most OLTP tables with nobody asked.

CI proves it: a job starts a pinned `cubejs/cube` against the test
Postgres with a fixture schema, loads the export, fails on any compile
error from `/cubejs-api/v1/meta`, and runs each agreed measure through
Cube and through SQLDesk, failing if the numbers differ. That comparison
is what "it works, move it to Cube" means in a test.

### B. Ask, never guess

When Cube needs something SQLDesk cannot know for certain, a person
provides it:

- **Primary key** where the engine declares none (most warehouses): the
  Catalog page lists the table under *Needed for Cube* with a column
  picker.
- **Join direction**: the harvest proposes one from how queries join; a
  curator confirms one-to-many, many-to-one or one-to-one. Unconfirmed
  joins are not exported.
- **Measures Cube's types do not cover** stay out until a curator confirms
  them as `type: number` with their SQL.
- **Cube's own credentials**: the Cube URL and the API secret SQLDesk signs
  its tokens with, entered by an admin. SQLDesk never generates them and
  never hands Cube a data source password; Cube gets its database
  credentials from its own configuration, one named Cube data source per
  SQLDesk data source.

A table with anything outstanding is left out of the export and listed with
what it still needs, so what reaches Cube always loads. `manage ai export
--check` prints the same list and exits non-zero, for a pipeline to stop on.
Answering these needs "Curate the catalog" (§5).

### C. Cube first, SQLDesk for what is new

- **Connecting a Cube, both ways (decided).** An admin gives a URL and
  secret for a Cube they already run. Or the chart runs one as an add-on,
  like Rendering: off by default, `cube.enabled`, reading the exported
  files from a volume, with its database credentials supplied in values.
  Both, because CI already needs the container, and minikube testing needs
  a Cube to point at.
- **Looking.** `find_context` and `find_measures` check Cube's model first
  (from `/v1/meta`, cached and refreshed with the harvest). A match is
  answered from Cube and marked as such.
- **Running.** Cube's SQL API speaks Postgres, so a connected Cube is an
  ordinary SQLDesk data source. `run_query` against it gets the same
  permissions, audit, read-only guard and time budget as any other source,
  and dashboards can use it too.
- **Falling back.** When Cube has nothing that fits, the answer comes from
  SQLDesk's catalog marked *not in Cube yet*. When Cube is unreachable, MCP
  answers from SQLDesk and says Cube did not respond; a Cube outage never
  stops an answer.
- **The Catalog page** shows, per table, what is in Cube, what is proven but
  not exported yet, and what is still needed.

**Verify:** the CI Cube job above; a table with no declared key is listed as
needed and absent from the export, never exported with a guessed key; an
unconfirmed join is absent; with a Cube connected, `find_measures` returns
Cube's measure first and labelled; with Cube stopped, the same call answers
from SQLDesk and says so; `run_query` on the Cube data source is refused for
a user without access to it.

## §8 Share a dashboard to Slack

**What people do:** Share → Send to Slack. Pick a channel, add a line of
text if they like, send. The channel gets the text, a small picture of the
dashboard, and an **Open dashboard** button. Only for a dashboard within the
one-page rule (12 widgets, one page), the same check export uses; a bigger
one says "Too big to send" at once, as export does.

There are three ways to get a picture into Slack, and they need different
things:

| | A. SQLDesk posts it | B. A public link that previews | C. Any link previews, internally |
|---|---|---|---|
| How | SQLDesk draws the picture, uploads it to Slack and posts the message | Paste the public link; Slack fetches the page and shows its picture | A Slack app watches for SQLDesk links being pasted and answers with the picture |
| Slack app with a bot token | Yes | No | Yes, in Socket Mode |
| SQLDesk reachable from the internet | **No** | **Yes** | No |
| Dashboard must have a public link | No | Yes | No |
| Rendering add-on | Yes | Yes | Yes |
| Works for an install on a VPN | Yes | No: Slack gets a bare link | Yes |
| Size | Medium | Small, once A's renderer exists | Large: a long-lived connection held by a worker |

**Decided: A only.** It works on a VPN, which is where most installs are.
B and C are not planned.

**A, in detail.**

- *Setup, once, by an admin:* create a Slack app in the workspace (the
  Deploying page gives a manifest to paste), install it, and enter its bot
  token in Settings → Slack. Scopes: `chat:write` and `files:write` to post,
  `channels:read` and `groups:read` to list channels. The token is stored
  encrypted, like data source credentials. For a private channel, somebody
  invites the bot first.
- *The picture* comes from the renderer through §1's one-dashboard pass,
  never a public link, and is **uploaded** to Slack rather than linked. So
  Slack never has to reach SQLDesk, and it works on a VPN. Latest stored
  results, with their age in the message ("as of 10:42").
- *The button opens the dashboard's public link (decided),* so anyone in
  the channel can open it without signing in, and the dialog says so before
  sending. A dashboard with no public link yet: its owner or an admin can
  turn one on from the dialog, the same switch and the same rule as Share
  today. Anyone else is told to ask them, and the button then opens the
  dashboard's own address, where people sign in. When the organization has
  public links switched off, the button always opens the dashboard's own
  address. Turning the public link off later is how a sent button stops
  working.
- *Who may:* sending a dashboard's contents to Slack is the same decision as
  mailing it, so §5's `send_subscriptions` becomes **`send_dashboards`**,
  "Send dashboards (email and Slack)". The message names who sent it.
- *Alerts get pictures too:* with a bot token in place, an alert's Slack
  message can carry its screenshot, which the webhook never could.

**Verify:** a message arrives with the picture and a button that opens the
public link, with SQLDesk unreachable from outside (the test Slack
workspace, or a stub of Slack's API in CI); without a public link the button
opens the dashboard's own address, and only the owner or an admin is offered
the switch; a too-big dashboard is refused before anything is sent;
a user without `send_dashboards` sees no Send to Slack; a bad or revoked
token says so in Settings; a private channel the bot is not in is not
offered.

## §9 Streams, and what SQLDesk does with data it holds

### The rule everything else follows

SQLDesk holds three kinds of data, and which one it is decides what may be
thrown away.

| | Who owns the truth | Losing it costs | Policy |
|---|---|---|---|
| **Borrowed** — a warehouse answer in `query_results` | the warehouse | a re-query | exists: unused results go after 7 days |
| **Owned** — an uploaded file | **SQLDesk, and nobody else** | the data itself | **none today** |
| **Flowing** — a Kafka topic | the broker, for its own retention | nothing; it is a window | does not exist yet |

Borrowed data may expire freely. Flowing data must be bounded *by
construction*. Owned data is the only copy, so it expires on a clock people
can see and stop -- never silently.

The missing half is not theoretical: on 2026-09-28 the development disk
reached 100% and took Postgres down with it, because nothing bounded what
SQLDesk was storing.

### A. Uploads get a life

- **Seven days by default.** An upload shows its expiry the moment it lands
  ("expires 6 October"), and the list shows a countdown. Most uploads are
  somebody checking a CSV once; those should not be on the disk in a year.
- **Keep, for those who may.** A `keep_uploads` permission (§5) turns an
  upload permanent in one click. The uploader is emailed the day before
  anything expires, with that button in the mail. **Nothing is ever deleted
  without a warning that a person could act on** -- it is the only copy.
- **Unloaded before deleted.** After three days unqueried the file stops
  being registered with DuckDB. It keeps its disk space and comes back on
  the next query; what it stops holding is working memory in every worker.
  This is the cheap, reversible half of the lifecycle and it runs first.
- **A byte quota for the whole install**, default 5 GB, checked at upload
  time with the number in the message: "this would take you past 5 GB; 4.6
  GB is in use, and 12 uploads have not been queried in a month."
  Keyed on `org_id` in the database, like every other scoped thing, so a
  multi-organization install counts each separately -- but no screen and no
  message says "organization", because on every install anyone runs there is
  one and it is called whatever they typed at setup.
- **A page that shows it.** Admin → Storage: per data source, what is held,
  how big, when it was last queried, what expires when. None of this is
  visible anywhere today.

### B. A stream is a window

A topic is a data source. SQLDesk keeps **the last few minutes of raw
events**, and **rolls everything older into per-minute buckets** it can keep
for a day. A dashboard asking "what is happening now" reads the raw window;
one asking "how does now compare to this morning" reads the rollup. Neither
needs SQLDesk to hold a day of raw Kafka, and it will not.

**For history, land the topic in your warehouse** with Kafka Connect or
Flink and point SQLDesk at the warehouse. The Data sources page says so where
somebody is about to ask for more retention.

*Where it lives:* DuckDB, one file per stream, under the same sandbox as
uploads. Columnar, so a few million flattened events are cheap; truncation is
a DELETE; and it keeps stream writes out of the application's Postgres, which
holds users, queries and dashboards and has to stay small enough to back up.
Rollups are small enough for Postgres and live there, so they survive a
restart.

### B2. Python moves bytes; DuckDB does the work

**The consumer never decodes a message.** It collects raw message bytes for
one second, then hands the whole buffer to DuckDB as newline-delimited JSON.
DuckDB parses it, stores it, and -- once a minute -- aggregates it. Sampling
hashes the key's bytes, so that needs no decoding either, and the schema is
inferred by `read_json_auto` rather than by us.

This was measured before it was chosen, on 200,000 events of ordinary JSON
(32 MB) on a two-core machine:

| | |
|---|---|
| Python `json.loads`, one message at a time | 250,000 events/sec |
| **DuckDB parsing the whole batch, no Python** | **914,000 events/sec** |
| **A rollup `GROUP BY` over those 200,000 rows** | **7 milliseconds** |
| Top 1,000 of 5,000 distinct keys | 4 milliseconds |

So **the aggregation is not the cost; the parsing is**, and the way to win
is to do neither in Python. At 50,000 events/sec a flush is 50,000 rows
parsed in about 55 milliseconds once a second, and the rollup is seven
milliseconds a minute over rows that had to be stored anyway.

The shape that falls out is simpler than a pipeline: there is no aggregation
stage. There is a buffer, a database, and one query a minute.

*Distinct counts are approximate by default* -- `approx_count_distinct`,
which is a HyperLogLog, and `approx_quantile` for percentiles. Exact is a
per-measure choice for the rare rollup that needs it. A dashboard counting
unique visitors per minute does not, and exact distinct is the one aggregate
that can cost more than everything else together.

### C. The window sizes itself to the rate

A fixed window is wrong in both directions: 30 minutes of a 50,000/s topic is
gigabytes, and 5 minutes of a 3/s topic is an empty chart. So the **row
budget is the real limit and the window follows from it**:

```
window = clamp(row_budget / observed_rate, 5 minutes, 30 minutes)
```

Default budget 5 million rows. A quiet topic gets the full half hour; a busy
one settles at five minutes. The window is recomputed as the rate moves, and
the dashboard says which it is: "last 6 minutes · 4.9M events".

### D. Rate limits, because this is the part that kills you

Three checks, at three moments:

1. **At setup.** Sniffing the topic for ten seconds before the data source
   saves, and saying what it found: *"this topic is doing ~48,000 events/sec.
   At your ceiling of 5,000/sec you will see a 1-in-10 sample."* The decision
   is made by somebody awake, not at 3am.
2. **While running.** A per-stream ceiling in events/sec and bytes/sec, and a
   global ceiling across every stream, so five busy topics cannot do together
   what one was not allowed to do alone.
3. **Over the ceiling: sample, and say so.** Deterministic sampling on a hash
   of the key's raw bytes -- no decoding -- so the same keys stay in and a
   count can be scaled back up honestly. The chart carries it: *"1-in-20
   sample · 480k events/min"*. **Never buffer the overflow** -- an unbounded
   queue in front of a slow writer is the crash, not the protection against
   it. The one-second flush is the bound: whatever arrives in a second is
   either written or sampled away within that second, and nothing queues
   behind it.

**Rollup cardinality is the other killer.** A rollup grouped by `user_id` on
a ten-million-user stream is not a rollup. Each stream declares its group-by
columns, distinct groups are capped (default 1,000), and everything past the
cap lands in a single `other` bucket that the chart shows rather than hides.

### E. Consuming only when somebody is watching

A stream is **active** when a dashboard or query using it was viewed in the
last 15 minutes, or an admin pinned it always-on. Otherwise the consumer
pauses and its window ages out normally.

Always-on burns a worker and a disk for a dashboard nobody has open;
consuming only while a dashboard is literally open means arriving to an empty
chart every time. This is the middle, and the pin covers the few streams that
genuinely need to be there at 3am.

**On resume, seek to the end.** The window is "now", so replaying an hour of
backlog to fill five minutes is waste. A consumer group per stream, so the
broker tracks us; a deliberate seek to latest, so we do not use it.

### F. Schema

`read_json_auto` over the first flush infers the columns; an admin corrects
and freezes them. **JSON first.** Avro and Protobuf need a schema registry,
which is its own connection and its own credentials -- 0.8.
A message that does not fit increments a `_malformed` counter the stream's
page shows; it never stops the consumer.

### G. What runs it

A consumer process per active stream, on the existing worker, with the same
pause-and-resume the scheduler already uses. One new setting for the broker
and its credentials, stored encrypted like every other data source's.

**Verify:** no message is decoded in Python on the ingest path (a test that
fails if `json.loads` is reached); a topic at 50,000/s does not grow the
window past its row budget
and is visibly sampled; a paused stream stops consuming within a minute of
its last viewer leaving; a rollup with 10,000 distinct keys caps at 1,000
plus `other`; an upload is unloaded at three days and still queryable; an
upload expires at seven and mails its owner first; a `keep_uploads` holder
stops that and nobody else can; an upload past the quota is refused with the
numbers in the message; Admin → Storage adds up to what is on disk.
