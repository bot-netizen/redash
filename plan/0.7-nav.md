# The navigation restructure

Decided with Iqbal on **2026-10-03**, for 0.7. This replaces the nav described
in [state.md](state.md); update that line when this lands.

## Why

The bar read `Dashboards ▾ · Queries · Kafka Streams ▾ · Catalog · Alerts ·
Settings ▾ · Admin ▾`, which mixed three vocabularies: objects you keep
(Dashboards, Queries, Alerts), a vendor (Kafka), and sections (Settings,
Admin). Naming one broker at the top of every page is the equivalent of a
**Postgres** tab beside Queries.

Three of the four items under `Kafka Streams` were duplicates, and not
arguably so:

| Menu item | What it actually was |
|---|---|
| Streaming Query | `/streams/query` — the query editor with a flag. A *create* action living in a nav menu. |
| Streaming Dashboards | `/dashboards/streaming` — the dashboards list, filtered. |
| Running Streams | Admin → Streaming Queries, minus the budget settings. |
| Manage Topics | The only genuine destination — and it is connection setup. |

The split had already produced defects: `Query#getUrl()` was stream-blind, so
a saved streaming query in the Queries list linked to `/queries/<id>`;
`QueryView` has no stream handling at all; and `QuerySource` carried code
whose only job was to bounce between `/streams/query/<id>` and
`/queries/<id>/source`. Code that exists to reconcile two URL spaces for one
object is the information architecture saying it is one object.

## The vocabulary

**`Streaming` is the kind. `Live` is the state.** Not interchangeable:

- `LiveBadge` already renders "● Live · every 30 seconds" and "Paused by
  Iqbal" — for **ordinary** dashboards too (`SAVED_INTERVALS`). `live` is also
  a column on `dashboards`. "Live" has meant *refreshing right now* since
  0.4.0.
- So "Live dashboards" for stream-fed ones would put one word with two
  meanings on one screen: an ordinary dashboard wearing a Live badge while
  filed under Dashboards, and a stream-fed one filed under Live.
- `Streaming` also matches everything already shipped: `kind=streaming`,
  `is_streaming`, `streams_only`, Admin → Streaming Queries, the release name.

**Never "Kafka" in the UI.** `streaming_source_types()` is asked of the
registered runners, so a second broker needs no new list and no new nav.

## The bar

```
Dashboards ▾   Queries ▾   Catalog   Alerts   Settings ▾   Admin ▾     [+ Create ▾]
```

Dropdowns carry **high-level destinations only**. All / Favorites / Mine /
Archived stay on the page, where they already are; repeating them in the menu
would be the same control twice.

```
Queries ▾                  Dashboards ▾
  Queries                    Dashboards
  Streaming Queries          Streaming Dashboards
                             ──────────────
                             <folders marked in_menu>
                             Browse folders…
```

- `Create ▾` gains **New Streaming Query**, gated on `use_streams`. That is
  the whole of what the old menu's first item did.
- A folder may hold both kinds. Folders are a *location* axis and kind is a
  *type* axis, so the folder view deliberately cross-cuts the partition —
  the only place both kinds appear in one list.
- Everything stays permission-gated as it is. With `streams.enabled: false`
  (the chart default) `currentUser.can("use_streams")` is false, so the
  Streaming entries, the Create item and the Settings tab all disappear
  together.

## The partition: no object in two lists

Iqbal's rule: *"all under queries will not show any live queries and vice
versa… no same info at two places."* So these are halves of a split, not two
filters over one set.

| List | Shows |
|---|---|
| `/queries`, `/queries/favorites`, `/queries/my`, `/queries/archive` | saved only |
| `/queries/streaming` and its three siblings | streaming only |
| `/dashboards`, `/dashboards/favorites`, `/dashboards/my` | saved only |
| `/dashboards/streaming` and its two siblings | streaming only |
| `/dashboards/folder/<id>` | both — the deliberate cross-cut |

**Search is the other deliberate exception.** `api/queries/search` feeds the
search box and the add-widget picker. Somebody searching by name does not know
which half a thing is in, and a search that silently hides matches is worse
than the overlap — so search returns both and badges the streaming ones. The
add-widget picker *is* partitioned, because the server already refuses the
wrong kind and offering something that will fail is worse than not offering
it.

## Kind is stored, not derived

A query's kind is its data source's type: one FK, stable, never empty.
Nothing to store — the serializer gains `is_streaming` and the list endpoints
filter on the join.

A dashboard's was derived from its widgets (`any(_widget_is_streaming(w))`),
which leaves a hole the partition cannot survive: **a dashboard with no
widgets is not streaming**, so a newly created one always lands in the saved
half and jumps to the streaming half when its first widget arrives. Under a
partition that reads as "my dashboard disappeared".

So `dashboards.kind` becomes a column, chosen at creation, backfilled from
today's derived value. Three things fall out of it:

- The partition is total and stable; nothing ever moves between lists.
- The widget guard (`handlers/widgets.py`, *"a streaming one or an ordinary
  one, never both"*) can say *why* a visualization was refused instead of
  refusing after the fact.
- The three-join `EXISTS` subquery comes off every dashboard list query.

## The sign on an open dashboard

Asked for explicitly: the kind has to be visible when the dashboard opens, not
only true in the database.

- A **STREAMING** chip beside the title, in the same teal pill the stream
  editor already uses (`queries.less`, `.query-stream-page`), plus the same
  left-hand band down the page so it survives scrolling.
- The existing `LiveBadge` keeps saying the *state* next to it: "● Live ·
  every 2 seconds", or "Paused" when nobody is watching. Chip says what it is,
  badge says what it is doing.

## Moves

| Was | Now |
|---|---|
| Kafka Streams ▾ | gone |
| Streaming Query | Create ▾ → New Streaming Query |
| Streaming Dashboards | Dashboards ▾ → Streaming Dashboards |
| Manage Topics | **Settings → Streaming Data Sources** |
| Running Streams (`/streams/running`) | folded into Admin → Streaming Queries |

**Streaming Data Sources** is Iqbal's name, over a recommendation of
"Streaming Tables". The risk it carries is two doors for one thing: a cluster
is added under Settings → **Data Sources** as type `kafka_stream`, and a tab
beside it called Streaming Data Sources invites somebody to add one there. Both
pages state the division — Data Sources links across to it, and the page says
clusters are added under Data Sources and this is where their topics are
turned on. Gated with `isAvailable: () => currentUser.can("manage_streams")`,
because `manage_streams` is a grantable feature and `settingsMenu`'s
`permission` field only understands `hasPermission`.

**Running Streams** was readable by everybody on purpose — its own comment:
*"a limit whose holders are invisible is a limit people file tickets about."*
Admin-only would re-create that dead end: with every slot taken, a normal user
cannot start a stream and has nothing to look at. So the page goes, and the
count moves to where it bites — the stream editor's status strip reads "4 of 5
stream slots in use", expanding to topic and watchers. `api/streams/running`
stays readable by all.

## Out of scope, deliberately

**An archived-dashboards list.** There is an `is_archived` flag and an Archive
action, but no list, no endpoint and no sidebar entry — an archived dashboard
is reachable only by URL. A real gap, and it was in scope while the dropdowns
were going to enumerate All / Favorites / Mine / Archived on both sides. They
are not, so nothing in this structure needs it. Left for 0.8.

## What landed

Commits `8d5a56ea` and `80dca069` on `release/0.7`. 2345 backend and 689
frontend tests pass; 17 mutations were applied to the new behaviour and all 17
were caught.

Backend

- `kind=streaming|saved` on `BaseQueryListResource` (covers All **and**
  Archive), `MyQueriesResource`, `QueryFavoriteListResource`.
- The same on `MyDashboardsResource` and `DashboardFavoriteListResource`;
  `DashboardListResource` already has it.
- `is_streaming` on the query serializer.
- `dashboards.kind` column, migration, backfill; `Dashboard.is_streaming`
  reads it; the widget guard compares against it.

Frontend

- `DesktopNavbar` and `MobileNavbar`: the two dropdowns, Create gains its
  item, Kafka Streams goes.
- Queries and Dashboards lists: the streaming partition, its routes, its
  sidebar.
- `CreateDashboardDialog`: the kind choice.
- `DashboardPage`: chip and band.
- `settings.menu.js`: Streaming Data Sources.
- `getUrl()` returns `streams/query/<id>` for a streaming query; `/queries/:id`
  redirects there, because a streaming query has no stored result and so no
  view page — the editor is its only page.
- `/streams/running` and `/streams/topics` redirect to their new homes. The
  running one has two destinations: the admin page for an administrator, and
  the streaming queries list for everybody else, who would otherwise meet a
  permission error on a path that used to be theirs.
- `QuerySelector` takes a `kind`, and the Add Widget dialog passes the
  dashboard's. Found while writing this up: the picker searched the ordinary
  list endpoint, so an ordinary dashboard was offered streaming queries and
  every such choice ended in the server's refusal -- after the choice had been
  made.

Docs: the permissions table in `administration.html`, the two switches in
`deploying.html`, and the navigation prose in the streams and dashboards
guides.

### Not reached by the deploy

The migration's backfill did nothing on the local cluster, because all ten
dashboards there are ordinary -- nothing has a streaming widget on it yet. The
column and the migration are exercised by `tests/test_migrations.py` and by
`test_kind_partition.py`, but the *backfill of real data* has not run against
anything. Worth watching the first time this meets an install that has
streaming dashboards.
